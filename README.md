# Fold UI — iPhone Duo animation study

一个网页 Demo：手机从「合上 → 半开 → 展开」，**屏幕空间、内容布局、铰链、景深与光影同时连续变化**。

白话版介绍（带 GIF 录屏）：[看完发布会，我用一个变量在浏览器里折了台手机](blog/README.md)。

三个页面：`#/` 是折叠研究，`#/cover` 是封面共享元素飞行实验，`#/handoff` 是参照 Apple 官网视频重做的图库 → 邮件＋图库的内外屏交接。

2026-09-12：交接页已修正展开方向、机身比例、柔焦范围；内屏左右分别展示邮件与图库；[参考视频、逐段分析与保真边界](docs/duo-reference.md)。

技术栈：**React + GSAP ScrollTrigger + CSS 3D**。没有 Three.js，没有 3D 模型，手机本体是纯 DOM。

```bash
pnpm install
pnpm dev      # http://localhost:5180
pnpm build    # 类型检查 + 生产构建
```

## 核心思想

不是「做一个折叠手机动画」，而是**做一个由单一标量驱动的空间 UI 系统**。

```
ScrollTrigger / 滑块 / 拖拽
            │
            ▼
        progress  0 → 1
            │
            ▼
   computeFrame(p, size)          ← src/fold/mapping.ts
            │
   ┌────────┼────────┬──────────┬──────────┐
   ▼        ▼        ▼          ▼          ▼
 铰链      相机      外屏      内容布局    运动模糊
 --fold   --cam-*  背面旋转   --t        --blur
   │        │        │          │          │
   └────────┴────────┴──────────┴──────────┘
                     ▼
              一个 CSS 自定义属性集合
```

所有通道都写在 **scope 元素**（`.fold-scope`）上，设备、应用 UI、章节文案从同一棵继承树里读取。
没有任何组件自己拥有动画状态。

实现细节：
- **只写 CSS 变量，不触发 React 重渲染。** 每帧只做 `style.setProperty`。
- **章节文案的淡入淡出也在 CSS 里算**（`--ch0..--ch3` 由 JS 写，`.chapter` 直接 `opacity: var(--ch0)`）。
- `prefers-reduced-motion` 下关闭待机浮动动画，折叠本身保留（它是用户滚动驱动的）。

## 几何：两块刚性面板

这是整个效果里最重要的一个决定：**手机的尺寸从头到尾没有变过。**

```
        hinge (x = panel-w)
             │
   ┌─────────┴─────────┐
   │  left             │  right
   │  不动的基准面       │  绕左边缘旋转
   └───────────────────┴─────────┘
```

- 左半：`transform: translateZ(-3px)`，恒定不动。
- 右半：`transform-origin: left center` + `rotateY(calc(var(--fold) * -1deg))`，`--fold` 从 `180` 走到 `0`。
  展开方向是**朝观众**（`-1deg`）：折面在 90° 时正对镜头，随后落到右侧摊平。

只有**两个平面之间的角度**在变，不是宽度从 300px 拉到 600px。

几个由此推出的结论：

| 现象 | 原因 |
| --- | --- |
| 合上时看到的是外屏 | 外屏就是折叠那一半的**背面**（`rotateY(180deg)`），它随面板一起转走，不需要淡出 |
| 折痕在展开后几乎消失 | 铰链宽度绑在 `--t-spine`；折痕本身用一条**非单调**曲线，展开后回落到很淡的残余 |
| 不会出现 z-fighting | 左半固定后退 3px；铰链线落在透视原点上，这 3px 在视觉上不可见 |

## 内容：同一块画布，逐半裁切

内屏 UI 是一个 **2 × panel 宽**的图层，被渲染两次 —— 左右各一次，各自被自己的平面裁切。

```css
.panel__screen-inner { width: calc(var(--panel-w) * 2); }
.fold-panel--left  .panel__screen-inner { left: calc(var(--bezel-x) * -1); }
.fold-panel--right .panel__screen-inner { left: calc(var(--panel-w) * -1); }
```

两次渲染的坐标系完全相同（都是 `x=0` 在机身左边缘），所以**一个元素可以横跨折痕**。

首页的封面就是这么做的：它在左半是全出血的正方形，展开后落到右半的详情面板里 ——
中途它会同时出现在两块屏幕上，各自跟随自己的平面。这比「交叉淡入」高一个量级。

## 进度映射

`p` 是原始进度，`pe` 是缓动后的进度（`easeInOutCubic`）。`fold = 180 × (1 − pe)`。

| 通道 | 合上 | 展开 | 变量 |
| --- | --- | --- | --- |
| 铰链角度 | 180° | 0° | `--fold` |
| 外屏 | 面朝相机 | 已转到背面 | `backface-visibility` |
| 相机缩放 | 由舞台高度反推（≤1.34） | 1.00 | `--cam-s` |
| 相机偏航 | 0° | 0°（中途峰值 26°） | `--cam-ry` |
| 相机横向 | 让折叠态居中 | 0 | `--cam-x` |
| 内容布局 | 单栏 | 双栏 | `--t` |
| 折痕 | 18px 转轴 | 5px 暗线 | `--t-spine` / `--t-crease` |
| 运动模糊 | 0px | ≤ 2.6px | `--blur` |

大部分内容通道由 CSS 从 `--p` 直接推导，不需要 JS 参与：

```css
--t-list: clamp(0, calc((var(--p) - 0.46) / 0.32), 1);
```

**例外是 `--t-crease`。** 折痕是唯一一个**非单调**通道：它只在玻璃真的被弯折时存在，
应该在折叠中途最深、展平后回落到很淡的残余。用 `clamp(0, p / 0.35, 1)` 这种斜坡写法
会让它在 0° 时停在最大值 —— 结果是在双栏 UI 正中间糊一条 40px 的暗带，
正好和「几乎看不见的折痕」相反。所以它由 `creaseAt(p)` 在 JS 里算：

```ts
const bent = windowAt(p, 0.02, 0.27, 0.58, 0.95)   // 中途到峰值
const residual = 0.14 * smoothstep(0, 0.18, p)      // 展开后的残余
```

实测：展开态折痕处的暗降从 4.0/255 降到 1.2/255，已经在感知阈值之下。

### 两个值得记下来的坑

1. **不要给带 3D 子元素的容器加 `filter`。** `filter` 会强制扁平化，整个折叠会塌掉。
   运动模糊只能加在内容层（`.panel__screen-inner`）上。而且 `blur(0px)` 仍然是一个 filter，
   会强制光栅化、让静止时的文字发虚 —— 所以只在真的有速度时才写 `filter`。

2. **`em` 认的是元素自己的 `font-size`。** 一个 `font-size: 3.15em` 的时钟，它的 `top: 2.5em`
   是 121px 而不是 38px，直接和下面的小组件重叠。所以这里用一个显式单位：

   ```css
   .ui-root, .cover { --u: calc(var(--panel-w) * 0.0453); }
   ```

   所有尺寸都是 `--u` 的倍数，和继承来的字号彻底解耦。

### 相机横向偏移是算出来的，不是调出来的

折叠态的投影跨度是 `[-panelW, panelW · cos(fold − yaw)]`。相机按这个跨度重新居中，
设备在整个展开过程中保持视觉静止，而不是在最后突然横移一下：

```ts
const span = Math.max(0, Math.cos(((fold - camRy) * Math.PI) / 180))
const camX = 0.5 * panelW * camS * (1 - span)
```

## 第二个页面：外屏 → 内屏的交接

外屏长在折叠那一半的**背面**，所以设备展开时它会物理地转走 —— 内容跟着一起消失。
`#/cover` 这一页要解决的就是这件事：让内容活下来。

做法是把封面**从面板里提出来**，停在相机空间里：

```
p = 0            内容在外屏上，和面板共面
 ↓  面板开始转走，但内容不动 —— 「脱开」
p ≈ 0.3 → 0.9    内容横跨折痕飞向右侧详情面板
 ↓
p = 1            落到详情面板，交还给被裁切、带玻璃反光的那一份
```

### 两端精确，中途自由

起止位置都是**算出来的**，不是调出来的，所以交接处对不齐的可能性不存在：

```ts
COVER_ART  = { cx: 0.5, cy: 0.46, w: 0.6 }   // 外屏内框的比例
DETAIL_ART = { x: 1.152, y: 0.287, w: 0.653 } // × panelW，和 `.ui-hero` 的终点同源
```

落地那一份（`.cf-hero`）和飞行的那一份读**同一组变量**（`--fly-x1/y1/w1`），
所以两边不存在「保持同步」的问题 —— 它们本来就是同一个数字。
实测两个交接点都对齐在 1px 以内。

### 这里踩到的两个坑

1. **飞行层必须是相机的兄弟，不能是子元素。**
   折叠到 165° 时，折叠那一半是**朝观众翘起来**的：它的远端在 z 上已经到 +93px。
   所以一个只「抬起几 px」的封面其实是在玻璃**后面**，被外屏盖住 —— 表现是封面直接消失。
   把它放进 `.fold-camera` 内部就永远绕不开这个深度排序问题。
   改成 `.fold-camera` 的**兄弟节点**（同样的盒子、同样的 transform、同样的透视），
   它在绘制顺序上就永远在相机之后，深度问题整个消失。

2. **别在 0.1 就开始飞。**
   第一版把飞行窗口设成 `smoothstep(0.1, 0.86, p)`，结果封面在右半还几乎侧对镜头的时候就飞过去了，
   看起来像飞出机身。窗口设成 `smoothstep(0.30, 0.90, p)` 之后，整个横跨过程里目标都在画面内，
   而且刚好在机身摊平的那一刻落地。
3. **飞行层也要被机身剪裁。** 飞行层虽然是相机的兄弟，但它会画在机身**上方**——
   如果它自己不带玻璃的轮廓，封面飞到屏幕外的位置时看起来就像飘在手机外面。
   现在飞行层里放了两块和面板完全相同的玻璃平面（`--fly-depth` 控制前后深度），
   封面永远被夹在屏幕轮廓内部，飞到哪里都不会跑出机身。

3. **billboard 只在空中生效。**
   封面需要在飞行时始终朝向观众，但两端必须是**共面**的，否则交接瞬间会有几度的错位。
   `--fly-bill = sin(πt)` 正好在两端归零。

## 交互

- **导航**：顶栏在「折叠研究 / 外屏交接」之间切换（hash 路由，构建产物丢到任何静态托管都能跑）。
- **滚动**：`Narrative` 用 ScrollTrigger `pin + scrub: 0.8`，约 2.9 屏的滚动量走完 180°。
- **拖动**：Playground 里可以直接上下拖拽机身。
- **滑块 / 预设 / 自动往返**：同一套 `apply(p)`。
- **切换应用**：播放器 / 邮件 / 图库，展示三种不同的「内容重排」策略。

## 如果要继续往上做

- **主页面也用共享元素**：`#/` 的封面目前还是两个同图元素交叉淡入伪装成移动；
  `#/cover` 已经把真实做法跑通了，可以直接搬过去。
- **真实铰链**：目前折面是零厚度的；加一段带半径的铰链几何可以做出真正的「外壳缝隙」。
- **WebGL**：只在需要真实反射/环境光时才值得上。手机用 Three.js、UI 留在 DOM，会是更好维护的分工。
